## 3. 这一轮的核心决定

### 3.1 网页由**模型**持有，不由视图持有

`WKWebView` 在 `WebBrowserModel` 里创建并强引用；`WebBrowserHost` 只是把同一个实例
挂进视图树、再挂出去。

**理由**：折叠面板或切走来源时 SwiftUI 会拆掉面板视图。网页归视图所有的话会跟着
被销毁，再展开就是一次重新加载——而花瓣登录一次很贵，用户的感受是「我刚登录完，
怎么又要加载」。这是产品负责人明确提的验收条件。

**请复核**：
- `WebBrowserModel` 被 `WorkspaceModel` **懒建**持有（`@ObservationIgnored private var lazyBrowser`），
  理由是 `HeadlessImport` / `SnapshotHarness` 也建 `WorkspaceModel` 而那些进程从不开窗口。
  懒建的写法（computed property 里首次读取时创建 + `@ObservationIgnored`）是否站得住？
- `dismantleNSView` 里把网页从父视图摘下来、但模型仍持有它的引用，这个生命周期有没有
  我没想到的坑（比如 WKWebView 长期不在视图树上时的内存或进程行为）？

### 3.2 导航状态不用 KVO

`canGoBack` / `canGoForward` / `isLoading` / `url` / `title` 都是 KVO 属性，但
`observe` 的闭包是 `@Sendable` 的，读不到主 actor 上的 `WKWebView`；绕过去只能用
`MainActor.assumeIsolated`，而它在不在主线程时会**直接崩**。改成由 `WKNavigationDelegate`
回调驱动（`didStartProvisionalNavigation` / `didCommit` / `didFinish` / `didFail`）。

**请复核**：手势前进后退（`allowsBackForwardNavigationGestures`）会不会有回调覆盖不到
的路径，导致前进/后退按钮的可用状态滞后？我的判断是手势也会走导航回调，但没有实测。

### 3.3 拖入从「认文件 URL」改成「认载荷」

画布原来只登记 `.fileURL`。**网页拖出来的图没有 `public.file-url`**——WebKit 给的是一份
promised file 加 `public.tiff` / `public.png` / `webp`（Spike 实测 29 项类型清单，
见报告 §8.2）。不登记这些类型的表现是 `draggingEntered` 根本不被调用，界面上一点反应
都没有，连失败都记不下来。

改法是复用粘贴通道早就有的形态类型 `ClipboardPayload`，而不是给拖入单开一条"位图路径"。

**两处请重点复核**：

1. **`performDragOperation` 里同步读剪贴板**。`NSDraggingInfo.draggingPasteboard` 只在
   拖放会话内有效，交给异步流水线等于去读一块已经被拆掉的板子。但同步读意味着
   `PasteboardReader.read()` 里的 TIFF→PNG 重编码（`reencodeAsPNG`）跑在主线程上。
   我判断这与 `⌘V` 那条路代价相同（同一条 `PasteboardReader`）、且网页图通常不大，
   **但这个判断没有测量支撑**。请判断要不要为此单独排一条异步化。
2. **`acceptedDragTypes` 从 1 种扩到 7 种**，会不会抢走原本该给别的接收者的拖拽
   （比如从其他 App 拖来的图片以前落到别处、现在被画布吃掉）？我自己想不到反例，
   但这条属于"扩大了自己接管的输入面"。

### 3.4 采集入口按产品负责人口头指示做

`⌘V` 沿用原有的标准选择器路径（未改动，搜索框里的 `⌘V` 仍然粘文字）；新增画布右键
菜单「粘贴图片」。**没有**在面板里加按钮——见 §1.1 第二条与 §6-①。

来源标注：拖入标 `.dragIn`，粘贴标 `.paste`。**没有假标记为 `.web`**，也没有把当前页面
URL 写成图片的来源证据（遵守计划书 §切片 B 的要求）。

## 5. 修掉一个既有 bug：面板把手跟不上鼠标

**症状**（产品负责人报告）：拖右边缘调宽时边框不跟鼠标，经常比鼠标跑得慢，
鼠标已经移出窗口了宽度还没跟上。

**根因**：拖拽手势用默认的**本地坐标系** `.local`，量的是把手自己那个坐标系里的位移。
而把手贴在面板右边缘——面板宽度正是被这次拖拽改的，**把手一边被拖一边跟着跑**。
鼠标右移 10pt、把手也右移 10pt，在把手自己的坐标系里鼠标等于没动过，位移自我抵消。

**修法**：`DragGesture(minimumDistance: 1, coordinateSpace: .global)`。

**为什么现在才暴露**：老的宽度上限 420pt 太窄，从 260 拖到 420 只有 160pt 的行程，
自我抵消的累积量小；本轮上限放开到 900，症状才明显。

**请复核**：这个诊断对不对。我没有构造一个可自动化的复现——**它是靠"改完就好了"
确认的，不是靠断言钉住的**。如果 Codex 认为该补一条回归断言，请指出可行做法
（我想不到怎么在无头环境里模拟一次真实拖拽的坐标反馈）。

### ① 面板内「将剪贴板图片放入画布」按钮 —— 未做

- 计划书原文：「网页面板只增加一个主按钮：**"将剪贴板图片放入画布"**」，
  理由是「侧栏按钮提供**不依赖焦点**的明确入口，不能通过全局抢占 `⌘V` 达成目标」。
- 我做的：`⌘V`（未改动）+ 画布右键菜单「粘贴图片」。
- **实际后果**：用户从网页复制完图片后，焦点在网页里，`⌘V` 会被网页吃掉；
  必须先点一下画布，才能粘贴。产品负责人的原话是「在画布上点击粘贴」，
  说明他知道要点击——但这是多一步，而且这一步在计划书里被明确判定为要消除的。
- **我的判断**：这一条大概率该补。成本低（`WorkspaceModel.paste()` 已经现成）。
  但它是已验收范围内的东西，需要产品负责人发话。**请 Codex 独立判断**：
  按计划书补按钮，还是把计划书这一条作废。

### ② Pinterest 快捷入口 —— 未做

计划书要求「提供 Pinterest 快捷入口和 `http(s)` 地址栏」。地址栏做了，快捷入口没做。

### ③ 浏览器面板独立宽度状态 —— 未做

- 计划书原文：「浏览器面板使用**独立于**普通素材面板的宽度状态。普通素材面板目前上限
  420 pt，而 Spike 浏览区要求至少约 520 pt……先以约 520–600 pt 实测默认 1280 pt 窗口」。
- 我做的：所有来源**共用** `panelWidth`，默认 260pt（`DesignTokens.Metrics.panelWidth`）。
- **实际后果**：第一次点开花瓣，拿到的是 260pt 宽的网页——页面的响应式布局会停在
  手机版。产品负责人验收时是自己拖宽的，所以这个默认值没被看见。
- 我的上限改动（420→900）只解决了"能拖多宽"，**没解决"首次打开多宽"**。

### 另有两项需要说明（不算偏差，但请确认）

- **来源标识仍是 `huaban`，未改成计划书建议的 `web`。** 计划书允许在"无持久化依赖"时
  改名。已核实：`MaterialSourceID` 只在内存里（`WorkspaceModel.activeSourceID` 是普通

- **计划书 §4 明确「现有『截图』提供者读取全素材库，所以网页粘贴的图也会出现在那里，
  这是已有命名与实际内容不一致，不是本轮再建一套网页图库的理由」——本实现遵守**，
