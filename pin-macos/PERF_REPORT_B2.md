| 卡顿计数 | >16.7ms **0** · >8.3ms **0** | >16.7ms **0** · >8.3ms **0** |
| 解码 | **3** 次（= 素材数） | 0 次 |
| 缓存 | 命中 76 · 未命中 4 · 存量 6.7 MB | 命中 96 · 未命中 0 |
| 建层峰值 | 28 个图层 | 28 个图层 |

**两件要看清的事：**

1. **扫描是 O(场景元素数)，不是 O(视口内元素数)。** `refreshVisibleContent` 对
   `elementModels` 里**每一个**元素做一次 `frame.intersects(rect)`，不管它可不可见。
   所以元素 300 → 1000（3.3×）时扫描中位数从 0.050 涨到 0.142 ms（2.8×），
   而**建层数在两边都是 28**——图层的数量被虚拟化控制住了，扫描的线性没被控制住。
   外推到 10,000 元素约 1.4 ms，仍在 8 ms 预算内，所以本轮不动；但这是一个**已知的
   线性项**，要压它得给元素加空间索引（网格或四叉树），那是一次单独的重构。
2. **冷扫和暖扫的解码数从 3 掉到 0，但每帧耗时几乎没变**（0.157 vs 0.158 ms）。
   这正是把解码放到主线程之外要换的东西：冷启动要付 3 次解码的代价，但那笔代价
   **不出现在任何一帧的主线程时间里**。

**这一栏的重复性**：上表的数字取自本报告这一次运行。同一台机器、同一份二进制连跑
三次（`--perf-report`），1000 元素冷扫的每帧主线程工作是：

| 运行 | 中位数 | P95 | P99 |
| --- | --- | --- | --- |
| 第 1 次 | 0.129 ms | 0.234 ms | 0.405 ms |
| 第 2 次（本报告） | 0.157 ms | 0.312 ms | 0.411 ms |
| 第 3 次 | 0.154 ms | 0.300 ms | 0.456 ms |

中位数在 0.13 ~ 0.16 之间、P95 在 0.23 ~ 0.31 之间——**你自己跑出来的数落在
这个区间内就是对的**，不必和本报告逐位相同。**建层峰值、解码次数、缓存统计、档位
这些结构性数字是确定的**，只有耗时会漂（三次里两次几乎一样，第一次整体偏低，
成因没有查——可能只是机器当时的忙闲）。

### 4.4 20 张 4K · 200% 走遍全部 → 20% → 回到 200%

单张 4K 解码后 31.6 MB（3840×2160×4B）。20 张全尺寸合计 **632.8 MB**，
预算 **512.0 MB** — **装不下**，下面记的就是这件事。

**① 200% 走遍 20 张**（程序化相机移动，见下）

```
解码次数       20（20 张各一次；虚拟化下只有真正进过视口的才解）
取消次数       0
缓存账面峰值   537.9 MB
缓存淘汰次数   4
进程 footprint 6.4 MB · 读写之后 513.5 MB
```

走遍用的是**程序化相机移动，不是手势**：一张 4K 在 200% 下宽 3840 点，任何真实的
滚动事件都跨不过它。相机直接写入走的是同一条 `adoptCamera` → 可见性 + 档位重算的
路径，虚拟化该做的事一件不少；造一个每帧几千点的滚动增量只会得到一条没有对应场景
的曲线。

**② 缩到 20%**（相机停在网格中央那张上，20 张这时全部可见）

```
建了图层的元素      20 / 20
需求                768×432 像素（元素 1920×1080 世界单位 × 0.2 × 屏幕倍率 2.0）
第 12 张（全程可见） 档位 原分辨率 → 1/2（收敛）
另一张（重新进视口） 档位 1/4   ← 缩放后才有图层，没有上一档
对照                全程可见那张若不做迟滞会是 1/4（`LODTier.fitting`）
迟滞的内存代价       留在 1/2（7.9 MB）而不是 1/4（2.0 MB）
新增解码            20 次 · 命中 0 · 未命中 20 · 淘汰 2 · 存量 488.5 MB
进程 footprint      450.9 MB · 读写之后 496.3 MB
```

**③ 回到 200% 再走遍 20 张**

```
重新解码       19 次 / 20    ← 这一栏是本节的重点
缓存           命中 1 · 未命中 19 · 淘汰 37 · 存量 506.2 MB
账面历史峰值   541.8 MB
进程 footprint 39.6 MB · 读写之后 513.8 MB
往返期间取消   0 次
```

#### 这一栏值得单独说：工作集大于预算时，LRU 会退化成反复重解

20 张全尺寸要 632.8 MB，预算 512.0 MB。**装不下。** 于是一路向前的扫描加上 LRU
退化成：刚解好的那张，在走到它之前就被后面的挤掉了。所以 ③ 里 20 张有 19 张要
重来一次。

这不是实现错误，是"缓存放不下整个工作集"的必然结果。它说明 **512 MB 这个预算在
"20 张 4K 全尺寸"这个场景下不够**——这是**一个待决的参数，不是可以顺手改掉的 bug**：

- 改成"物理内存 1/4"会到 512 MB 的上限（`maximumByteBudget` 夹着），也仍然不够；
- 真正的解法不在预算大小上，而在**策略**上（比如"全尺寸不常驻，只保留当前视口
  附近的那几张"，或者"视口外降档保留"）。这属于 B2 之后的决策，本轮不动。

### 4.5 档位边界上的抖动 —— 迟滞真正要解决的场景

4.4 的 ② 量的是"大幅缩放之后的稳态档位"，**它证明不了迟滞的价值**：大幅缩放时
终点那一档本来就没有余量，迟滞只是把降档拖慢几轮，稳态迟早落到同一档。
迟滞真正的用处在需求正好骑在一条档位边界上的时候——手指搭在触控板上轻微抖动、
或者一次捏合停在临界点。

边界位置是**算出来的**：`fitting` 在 k 与 k+1 之间的分界是 `demand = original / 2^(k+1)`。
两条臂除 `lod.downgradeHeadroom` 外完全相同。

```
抖动中心     缩放 0.1250 —— 1/4 与 1/8 的分界（需求 480 像素宽 = 原图 3840 / 8）
抖动幅度     ±2% · 24 次，每次都跨过边界

有迟滞（1.414）          换档 0 次 · 解码 0 次 · 存量 4.0 MB · 终点 1/4 → 1/4
无迟滞（1.0，B1 的行为）  换档 192 次 · 解码 2 次 · 存量 4.9 MB · 终点 1/4 → 1/4
```

**两条臂的终点档位相同、抖动次数与幅度相同，只有 `lod.downgradeHeadroom` 不同**
——所以"换档次数"这一栏的差别只可能来自迟滞本身。192 = 8 个可见元素 × 24 次抖动：
没有迟滞时，**每一个元素在每一次抖动上都换了一次档、发了一次请求**。

无迟滞那条只解码 2 次（两个档位各一次，之后都是命中），因为两个档位都还装得下缓存；
**缓存装不下时，每一次换档就是一次重解**——4.4 的 ③ 记的就是那个代价。

### 4.6 内存压力响应

```
填满之后       预算 512.0 MB · 账面存量 506.2 MB · footprint 7.7 MB · 读写之后 513.5 MB
收到 warning   预算 256.0 MB · 存量 253.1 MB · 淘汰累计 12 · 重新解码 0 次 · 读写之后 260.0 MB
收到 warning   预算 128.0 MB · 存量 126.6 MB · 淘汰累计 16 · 重新解码 0 次 · 读写之后 133.3 MB
收到 critical  预算  64.0 MB · 存量  63.3 MB · 淘汰累计 18 · 重新解码 0 次 · 读写之后  69.9 MB
```

**压力是构造的**：调的是 `ImageCache.handle` 这个产品入口，不是等系统真的报压力
（真实压力在测试里造不出来）。能证明的是"收到压力之后缓存会跟着收缩到预算以内"，
**不能**证明"系统真的报压力时一定如此"。

预算收缩是单向的：系统报"压力回到正常"不代表可以长回去，恢复靠下次启动
（`ImageCache.handle` 的说明）。

## 5 边界（这一节和数字一样重要）

### 5.1 这些数字**不是帧率**

1. **本进程没有窗口。** `CATransaction.commit()` 只是把图层改动写进渲染树；
   真正的合成、显示链路与垂直同步在 WindowServer 里，这里量不到。所以每一个数
   都是**每帧主线程工作耗时**，不是帧时间，也不是帧率。
2. `input` 是外层（一次输入走完「输入 → 档位 → 提交」），`scan` / `commit*` 是它的
   **内层分解——包含关系，不能相加**。把分解项加起来当帧时间是这份报告最容易犯的错。
3. 「>8.3ms」的计数**不等于掉帧数**：主线程工作只占一帧的一部分。
4. 图片解码**不在主线程**，所以解码耗时不出现在任何一栏里。它的代价只体现在
   「冷扫 vs 暖扫」的解码次数上。
5. 异步解码结果落到 `layer.contents` 时**没有显式事务**，那一段提交不在 `commit`
   的样本里。
6. **进程 footprint 看不见未被触碰的 purgeable 页**，而 CoreGraphics 位图上下文的
   字节正是这么分配的。所以"footprint"那一栏是下界，"读写之后"那一栏才是缓存真正
   占着的量级。这是本轮实测发现的一个**测量陷阱**，细节见 §6.1。
7. 玻璃面板常开，但材质合成在系统侧，这里完全没有它。
8. 素材是**合成**的（平面色块 + 细线），真实照片的像素熵高得多。解码耗时与内存都
   受这一点影响——**合成素材偏乐观**。

### 5.2 本报告**不含**的东西

- **帧率、GPU 占用、真机手感**：需要人工跑一次 Instruments。signpost 已接好
  （subsystem `com.pin.native.canvas`，category `PointsOfInterest`），
  **但本报告不代表那一步做过**。
- **SwiftUI 场景建立、存储准备、窗口创建、首帧上屏**：本进程没有窗口，这几项不存在。
- **真实素材的导入与解码**（批次 C）：本轮全部是程序合成素材。
- **玻璃面板的开销**：见 5.1 第 7 条。

## 6 这一轮实测顺带确认的三件事

### 6.1 `phys_footprint` / `resident_size` 看不见未触碰的 purgeable 页

第一版报告用 RSS 审计图片缓存，量出"20 张 4K 只占 6.4 MB"这种明显不对的数。
四个对照实验确定了原因：

| 实验 | 结果 |
| --- | --- |
| 创建 16 张 4K `CGImage`，立刻量 | footprint **2 MB**（RSS 33 MB） |
| 把每张**画一遍**（触碰每个页面），再量 | footprint **509 MB**（账面 506 MB）✅ 对上了 |
| 普通 `malloc` 512 MB 并写入 | footprint **513 MB** ✅ 说明工具本身没问题 |
| 用不可压缩的噪声图重复上面两步 | 与色块一致，排除压缩解释 |

结论：**CoreGraphics 位图上下文的字节是 purgeable 分配的，没被触碰过的页面不计入
footprint。** 所以报告里两个数都给：「footprint」（下界）和「读写之后」（把缓存里
的像素逐张读一遍再量）。**用 RSS 审计图片缓存会得到一个偏小一个数量级的答案，
而且看起来很正常。**

### 6.2 迟滞的逐级降档需要"再扫一次"才走一步

降档是"每扫一次往下走一级"，而扫描只由两件事触发：**相机写入**、**一次解码落地**。
所以一次缩放之后档位要过若干轮才停住。

第一版的收敛判据是"连续两次读到同一个档就算停住"，在 40 ms 的等待下会**假收敛**：
同一台机器上给出过 `1/2` 和 `1/4` 两个"收敛值"，两个看起来都很正常。
修法是每轮**推一下相机**（1 个世界单位），让每轮确定地产生一次扫描，并要求连续
两轮不变才算停住。

### 6.3 一次真实的测量事故：换显示器 = 换档位

见 §2 的警告框。同一份代码、同一条命令，因为主显示器从外接 1080p@1× 换成了内建
Retina@2×，同一场景量出的档位差了一级，两组数都对但不可比。**报告必须连显示器
与屏幕倍率一起给**，否则读者会拿两次运行的数去比较。
