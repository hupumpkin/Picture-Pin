### 3.1 数据层（`Sources/PinNative/Persistence/`，新目录）

| 文件 | 职责 |
| --- | --- |
| `Database.swift` | GRDB 连接（`DatabasePool` + WAL）、迁移器、打开失败抛 `DatabaseOpenError` |
| `Schema.swift` | v1 建表，逐条 `migrator.registerMigration` |
| `AssetStore.swift` | 素材落盘与读写（唯一入口） |
| `SceneStore.swift` | 按 board 读写元素、绘制顺序（**选中不持久化**，§7 第 6 条） |
| `LibrarySnapshot.swift` | 恢复用的只读快照（主线程读它，不直接读库） |

schema v1（列名待写时定，这里记语义）：

- `board(id, name, created_at, sort)`
- `asset(id, original_filename, relative_path, byte_count, content_hash, pixel_width, pixel_height, exif_orientation, kind, origin, added_at)`
- `element(id, board_id, asset_id, x, y, w, h, z)`

**既不存相机，也不存选中状态**（产品负责人已确认）：

- 相机每次启动回到 `.initial`。`board_view` 这类表**不建**，避免下一轮有人顺手把相机写进去
- 选中态**不是持久状态，而是撤销历史里的一步**：选中 A → 改选 B → 按撤销回到
  "选中 A"（撤销本身属后续开发，归 Codex 的 `SelectionController`）。它属于撤销栈，
  写进库会变成第二处真源，而"重启后还选着上次那个元素"对用户没有意义

写入策略：

- `DatabasePool` + WAL；**读在主线程、写走 writer 队列**
- **拖动中不写、松手后写**——拖动是最高频写入源，每次都写会直接吃掉
  §2.4 的主线程 P95 < 8ms 预算
- 退出（`applicationWillTerminate`）与切画布时强制刷盘
- 写入粒度与 `CanvasSceneCommand` 对齐：命令 → `CanvasSceneChange` → 落库

### 3.2 真解码（`Assets/FileImageProvider.swift`，新文件）

实现已有的 `ImageProvider` 协议（B1 定好、B2 沿用，注释里已经写明 C 的前提）：

- `metadata(for:)`：`CGImageSourceCopyPropertiesAtIndex` 读 `kCGImagePropertyOrientation`，
  返回**摆正之后**的尺寸（协议注释里的约定）
- `image(for:targetPixelSize:)`：`CGImageSourceCreateThumbnailAtIndex`
  + `kCGImageSourceThumbnailMaxPixelSize`——**走缩略图路径，不整幅解码再缩**
  （超长图整幅解码的峰值内存会很难看）
- 方向必须显式开 `kCGImageSourceCreateThumbnailWithTransform`，并写断言钉住；
  **实测**而不是按记忆断言（B2 吃过一次"凭印象以为同构"的亏）
- 解码在非主线程执行器；缓存复用 `ImageCache`（按 素材 × 档位）
- `.missing`（文件不在）/ `.failed(原因)`（ImageIO 报错）/ `.cancelled` 三个分支打通
- 格式**不写白名单、不设上限**：能解码就收，判定只走 ImageIO；失败文案统一为
  "这个文件不是能解码的图片"。扩展格式 = 不改判定逻辑

### 3.3 采集第一条通道：本地导入

`Import/ImportCoordinator.swift`（新）——三条通道共用的唯一入口，C1 只接文件选择器：

1. 复制**原字节**到 `assets/<uuid 前两位>/<uuid>.<原扩展名>`，**不转码**

### 3.9 内存策略（产品负责人已定的两条口径）

1. **视口外不留全尺寸**：元素离开视口后，把它的高档位像素从缓存里降下来（只留小档位）。
   代价是**拖回视口的那一瞬间会先糊一下再变清晰**（产品负责人已知并接受）；
   换来的是工作集不再随"看过多少张图"无限增长。这一条正对着 B2 实测到的边界：
   20 张 4K 全尺寸 632.8 MB > 512 MB 预算，LRU 退化成反复重解（20 张里重解 19 张）。
2. **尺寸上限**（注意：这是尺寸，不是格式白名单——格式仍然不写死）：
   - 导入时拒绝离谱文件：默认**最长边 > 40,000 或总像素 > 2 亿**，提示"这张图太大"，
     且不留下半成品素材
   - 单次解码分配上限：默认**≤ 64 MP（约 256 MB）**，任何一张图都不会把内存顶穿
   - 两个数都放在 `ImportPolicy` / `DecodePolicy` 里集中定义，改一个数就能调整

   这两条都要靠 C2 的 §2.4 复测来验证是不是真的压住了（顺带收数，不进出口条件）。

**验收反馈的缺陷修复：透明 PNG 显示灰底（2026-09-18）**：

产品负责人在真机验收时导入一张带透明通道的 PNG（3D 元宝素材），画布上显示
成"图带一块灰底"。根因在元素图层：底色（占位色）画在 `contents` 后面，图片
的透明区域把它透了出来——旧注释里"它也是带透明通道图片的底，所以图片到了
之后也不清掉"正是这个行为的出处，属于**有意保留、但方向错了**的设计。

修法：**真图到位就整块撤掉底色**（`finish` 的真解码路径与 `requestImage` 的
缓存种子路径都改），透明区域透出画布本身；"首图就绪之前"的占位底色与失败态
的失败色不受影响（后者正是"这块地方一眼就是坏的"那个信号）。新增查询入口
`sublayerHasBackingColor` / `hasBackingColor`（与"是不是失败色"分开问：
颜色取值可以改，"透明区域前不许垫东西"这条判据不能改）。

补 10 条断言，自检 616 → **626**：

- 真解码组（§3.2）+6：`CGImageDestination` 真写一张带 alpha 的 PNG（四周
  透明、正中实色、上下左右对称——对称让位图行序翻转无法把断言弄假）；
  先独立确认文件本身带 alpha；**逐像素读回**透明角落 alpha=0、不透明区
  未误伤；缩略图路径（`CreateThumbnailAtIndex`）同样保住透明；渲染器
  冷缓存路径真解码落地后不留底色；拖出再拖回、种子路径同样不留底色
  （第一帧的断言不 await——隔一次 await 就变成在验另一条路）。
- 图片→图层组（基线）+1：真图到位之后图层不留任何底色。
- 重试组（第一批）+1：成功之后底色整块撤掉（原来是"换回占位色"）。

- 大库的首次恢复时间没有基线（§2.4 的启动目标 800ms 是空画布口径）
