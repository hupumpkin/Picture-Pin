## 场景 → 渲染器：唯一同步通路

审核 P1-01 的返修。**第一版这里是个真缺陷**：`applyExternalScene` 在场景 revision
变化时只送 `order` 和相机，从不送 `inserted`/`updated`/`removed`，协调器初始化时
也不做全量同步。后果是批次 B 往画布放第一个元素时它不会出现——而那时离缺陷引入
已经过去一整个批次了。

现在的契约：

```text
SwiftUI 改场景  ──┐
perform(命令)   ──┼─→ Coordinator.scene ──→ scene.change(from: syncedScene)
挂载时全量同步  ──┘                              │
                                                 ▼
                                  CanvasRenderUpdate(change:)  → LayerRenderer
```

- `CanvasScene.change(from:)` 是**纯函数**，算差异不建图层，可以独立断言。
- `CanvasSceneChange` 自带 `order`，所以一份变更可以**原样**交给渲染器，不必补字段。
- 协调器保存 `syncedScene`（上一次同步过去的场景），差异以它为基准——
  不用渲染器的内部状态当基准，那会分叉。
- `LayerRenderer` 现在真的建图层了：`insertLayers` / `updateLayers` / `removeLayers` /
  `applyOrder` 全部有实现，图层生命周期完整。**图层的 `contents` 是空的**，
  只有一层占位底色——图片解码、LOD、缓存仍然归你（批次 B），占位底色随之删除。

闭环断言在 `--selftest` 里，读的是**真实 CALayer 树**（`sublayerIDsInDrawOrder`），
不是渲染器自己的字典。把缺陷改回去会挂掉 7 条断言（验证过）。

### 一、素材来源：从 enum 变成目录

第一版是 `enum MaterialSource: String, CaseIterable` 加**四处 switch**（标题、图标、
空状态标题、空状态说明），分散在 `SourceRail.swift` 和 `MaterialPanel.swift`。
加一个来源要改所有来源共享的类型定义和两个视图文件。

现在：

| 文件 | 内容 |
| --- | --- |
| `Materials/MaterialSource.swift` | `MaterialSourceID`（字符串标识）、`MaterialSource`（描述）、`MaterialSourceCatalog`（目录） |
| `Materials/MaterialProvider.swift` | `MaterialItem`、`MaterialSourceContent`、`MaterialProvider` 协议、批次 A 的占位实现 |

- **加一个来源 = 在 `MaterialSourceCatalog.make(environment:)` 里加一条数据。** 视图、类型定义都不用动。
- 空状态文案住在 `MaterialSource` 上，不再散在面板的 switch 里。
- 面板不认识任何具体来源，只认三样：描述、内容状态、内容形态。
- **内容状态四种齐全**（`idle` / `loading` / `loaded` / `failed`）。这是刻意的：
  素材读取、花瓣采集、字体枚举三者都是异步且可失败的，只写 `.loaded` 的话批次 C
  一定会以"先同步读一下"起步并漏掉失败分支——而失败的表现是「面板一直空着」，
  和「确实没有素材」长得一模一样。
- `MaterialSource.Surface` 现在只有 `.collection`。花瓣要在面板里内嵌浏览
  （路线图 §6），那是**内容形态确实是新的**，加一个 `case browser` 和一个视图。
  加了之后 `MaterialPanel` 会编译不过，直到新形态被实现——遗漏是编译错误，不是空面板。

**给批次 C 的接口**：实现 `MaterialProvider`（`environment` + `content` + `refresh()`），
在 catalog 里把 `PlaceholderMaterialProvider(environment:)` 换掉即可，**面板一行不用改**。
协议上有三条约束：实现方必须是 `@Observable` 的类（否则写进 `content` 后面板不重绘，
协议约束不了，只能靠约定）；`refresh()` 不抛错——失败写 `.failed(原因)`；
**数据目录从 `environment` 拿，不要自己调 `AppEnvironment.resolve()`**——
那是第二处真源，自检里有断言盯着这一点（见下节第三条）。

## 三处 P1 返修（VERSION_HISTORY 2026-09-17）

产品负责人本轮在 `VERSION_HISTORY.md` 的 2026-09-17 条目里记了三条，三条都改了。

### 一、换画布不清覆盖层

`applyExternalScene` 原来换画布时只同步场景，`overlay` 原样留着。覆盖层是**宿主全局
状态**，而选择框的坐标是 world 坐标——换到另一块画布后，旧画布的选择框会照着新画布上
同样的位置继续画。表现是「切了画布，画布上有个蓝框，元素根本不在那儿」。

修法：`applyExternalScene` 比对 `scene.boardID`，换了才 `discardOverlay()`。

**只在换画布时丢**，同一块画布的场景更新不清——元素被拖动时选择框必须跟着走，那不是
脏数据。两条断言把两个方向都钉住：

- 「同一块画布的场景更新不清覆盖层」——防止修过头（改成每次同步都清）
- 「换画布丢掉覆盖层」

注入缺陷（删掉 `if boardChanged { discardOverlay() }`）→ 红一条，报出「换画布丢掉覆盖层」。

### 二、交付清单不拒绝未登记的新文件

`manifest.sh --check` 原来只做一件事：逐条校验**清单里已登记文件**的哈希。
清单里没有的文件它根本不看。于是往 `Sources/` 加一个新文件、不重新生成清单，
校验照样通过——「不可变交付边界」是漏的，而漏掉的那类文件（新写的源码）
恰恰是复审最需要看到的。

修法：校验哈希之前先比**文件集合**，把两侧差集打印出来（「未登记」与「已消失」）
并以 1 退出。

两个分支都实测过：

| 分支 | 做法 | 结果 |
| --- | --- | --- |
| 未登记 | 真实树里造一个临时文件 | 报出文件名，退出 1（用完即删） |
| 已消失 | `mktemp -d` 探针树里删掉一个文件 | 报「已消失」，退出 1 |

已消失那一半在探针树里做，是因为**在真实树上删文件做验证会真的破坏工作区**。

### 三、真实素材提供者缺按环境注入的目录

这条是「两条预留接缝」的后续：`MaterialSourceCatalog` 当时还是个 `static let`，
批次 C 的实现拿不到数据目录，只能自己再解析一次环境——那就有了第二处真源，
而「界面读 dev-cc、面板读 dev-codex」不会有任何编译错误。

改法两步。第一步把目录变成函数（`static func make(environment:)`）。第二步是复核时
自己不满意又补的：**只有参数、没有消费者的话，"模型有没有把它传下去"在运行时观察不到**
——一个"在那儿但没接线"的参数正是这个项目反复出现的那类问题（P1-01 的场景同步就是）。
所以注入提上了协议：

```swift
@MainActor
protocol MaterialProvider: AnyObject {
    /// 由 MaterialSourceCatalog.make(environment:) 注入。
    var environment: AppEnvironment { get }
    var content: MaterialSourceContent { get }
    func refresh() async
}
```

这样它既是契约要求，也能在自检里断言。断言分两层、每个来源各一条：

- 「<来源> 的提供者拿到的是 codex 的目录」——是传进去的那份，不是自己解析的
- 「模型建的 <来源> 提供者拿到的是模型的目录」——模型确实交下去了

两次注入实测：

| 注入 | 结果 |
| --- | --- |
| 截图提供者改用 `.resolve()` | 红两条。报出的目录是 `Pin/dev-cc`（进程默认），注入的是 `dev-codex` |
| 模型改用 `.resolve()` | 红三条，全在「模型建的……」。catalog 三条仍绿——分层是对的，`make` 没坏，坏的是调用方 |

## 图片管线（批次 B1）

批次 A 的画布是空的（`layer.contents` 为空，只有占位底色）。B1 把像素接上，
**但不动交互**：换档策略、视口虚拟化、性能实测都属于 B2。

### 一、`Assets/` 是接缝，不是实现细节

`CanvasElement` 存的是 `AssetID`（元素只引用素材、不拥有它），所以渲染器需要一条
把 `AssetID` 变成像素的路。这条路**必须在批次 C 的真素材库之前定下来**：接口晚一步
到位，第一批实现就会绕开它——渲染器会自己长出解码与缓存，批次 C 再想共成就得把
渲染器拆开。

三个类型各管一件事：

| 类型 | 管什么 | 不管什么 |
| --- | --- | --- |
| `ImageProvider`（协议） | 元数据 + 取像素两个方法 | 不规定从哪来、不规定怎么缓存 |
| `ImageCache` | 纯存储：进、出、按字节预算淘汰 | 不发起解码、不知道素材从哪来 |
| `SyntheticImageProvider` | 合成素材、后台解码、并发请求合并 | 不画到图层上 |

**缓存不在渲染器里**，由 `WorkspaceModel` 持有并向下注入。三条理由，每条都会真的出错：
素材面板和画布必须共用一份（各缓存一份则同一张图解两遍）；切画布不该清空（按素材存，
不按元素、不按画布）；预算要有单一出口（只有一处知道总字节数，才谈得上淘汰）。

`LayerRenderer.init(images:)` **刻意没有默认值**。有默认值的话"忘了接线"会编译通过，
表现是画布上什么都不显示——而"参数在那儿但没接线"正是这个项目反复出现的那类问题
（见「三处 P1 返修」之三）。加参数时编译器报出 4 个调用点，必须逐一接上。

### 二、档位为什么是离散的（这条决定了后面所有事）

`LODTier` 是 2 的幂的档位（0 = 原图、1 = 1/2、2 = 1/4 ……），**不是"当前需要多少像素"**。
原因只有一条但它压倒一切：**档位是缓存键的一部分**。拿连续尺寸当键的话，每一级缩放
都是一个新键，缓存等于不存在——而缩放恰恰是最需要缓存的交互。

数字（自检里有断言钉着）：一张 4K 图解码后 3840×2160×4B = **31.6 MB**，
路线图 §2.4 要测的 20 张不同的 4K 图全按原分辨率留着就是 **632 MB**。
1/4 档省 16 倍。缓存预算默认 512 MB，是起步值，B2 按实测重定。

### 三、换档策略：保守式（不插低清中间态）

产品负责人选定的策略：**目标档位的像素没到之前，保持当前档位不动**，
不先插一张低清的过渡图。

代价要写清楚：既然不插中间态，**"糊多久"就等于"解码多快"**——延迟直接变成画质感受。
所以配套的三件事是必须的，不是优化项：解码必须在后台（有断言）、预加载要有余量、
档位边界要有迟滞（迟滞属于 B2）。

两种"不闪白"要分开，它们的做法不一样：

- **已有元素换档**：保留旧图，新图到了再原子替换（`requestImage` 里不清 `contents`）。
- **元素首次出现**：没有旧图可留，只能靠占位底色顶到首图就绪。
  占位底色因此从"这里有个元素"变成了"首图就绪前的顶替"，模块注释里写明了。

### 四、异步结果回来时，世界已经变了

这是整条链路上最容易出微妙 bug 的地方，四张状态表合起来解决它：

| 表 | 挡什么 |
| --- | --- |
| `assetPixelSizes` | 换档判断是同步的，不能每次都 `await` 元数据 |
| `missingAssets` | 已确认不存在的素材不必每帧重问 |
| `displayedTier` | **档位没变就不发请求**——缩放时不重复解码的全部秘密 |
| `imageGeneration` | 丢弃迟到结果。没有它的话，连续缩放时先发的后到，**画面会退回旧档位**，表现为"越缩放越糊" |

最后一条有专门造的竞态断言：把粗档的解码拖慢 0.5 秒，放大让细档先到，
再等过 0.5 秒确认画面**没有**被迟到的粗档换回去。注入缺陷后这条变红。

### 五、自检为什么会变成 async（`main` 为什么改成 `async`）

图片管线天生是异步的，断言必须 `await` 才能验。不这么做只剩两条更差的路：

- 在同步 `main` 里抽干 RunLoop 等 Task：主 actor 被占着，能不能推进全看 RunLoop
  顺不顺带跑主队列——**出问题时的表现是挂住，不是失败**，比报错难查得多。
- 把断言写成"发起请求"就结束：等于不验。

`PinNativeEntry.main` 因此是 `async` 的。同理，验证"换档瞬间图层里还是旧档像素"
这类**不该发生**的事，用有上限的轮询是错的（轮询看不见"中间有没有空过一帧"），
只有一处固定 `sleep` 是对的，代码里注明了理由。

### B1 断言怎么验的（缺陷注入实测）

每条关键断言都注入过对应缺陷，确认红的是**预期的那些**、且只有那些：

| 注入的缺陷 | 变红的断言 |
| --- | --- |
| 选档只看宽度 | 1 条（细长图那条） |
| 不设最粗档上限 | 1 条 |
| 按精确尺寸解码而不按档位 | 4 条 |
| 未知素材报成解码失败 | 1 条（`missing` 与 `failed` 分不开） |
| 解码留在主线程 | 1 条 |
| 允许淘汰比预算还大的那张 | 2 条 |
| 按 width × height × 4 记账 | 1 条 |
| 缓存永不命中 | 6 条（含两条换画布断言） |
| 档位没变也重复发请求 | 1 条 |
| 迟到结果不丢弃 | 1 条（画面被换回糊的） |

两条断言是**注入之后才发现原本没牙**，改了断言本身：

1. **记账口径**：原本用 64×64 的图验证"按行宽而不是 width×4 记账"。64 像素宽的行
   本来就是对齐的，两种算法给出同一个数——**无论实现对错都通过**。改成 100×100
   （行宽 416 而不是 400），并加一条断言守住"这张图的行宽确实带填充"，
   免得哪天平台的对齐规则变了、断言悄悄失去意义。
2. **不重复发请求**：原本同步数请求次数，而请求是异步发出去的，同步数一定数到
   请求之前的值——同样是**不管实现对错都通过**。改成先等 60ms 再数。
   这是全文件唯一一处固定 `sleep` 是对的：要等的是一件"不该发生"的事，
   而"不该发生"没有可轮询的终点。

### 已知边界（留给 B2）

- `refreshImageTiers()` 是 **O(元素数) 的线性扫描**，缩放时每帧走一遍。
  O(10²) 元素无所谓，**1000 元素时这里是第一个热点**，视口虚拟化要先把它收窄。
- **没有迟滞**。档位边界上来回微调缩放会反复换档（每次都要解码）。
- 缓存有预算和 LRU，但**没有内存压力响应**（`didReceiveMemoryWarning` 那一类）。
- **没有性能数字**。B1 不测帧时间——口径按 §2.4，属于 B2 的实测报告。
- 换画布不重解码有断言，但**"来回切不卡"要人手动确认**（`⌘⇧B`）。

## 手感参数与画布越界（B1 收尾，产品负责人实测后追加）

产品负责人实测后提了两件事：**手感对了，但参数别写死**、**合成素材盖住了左侧
截图面板**。前者是接线问题，后者是一个真实的图层 bug。

### 一、手感参数：从字面量收成 `MotionConfiguration.Feel`

第一版的手感数字是**散在四个文件里的字面量**：`1 + delta.height * 0.01`
（`MinimalInputAdapter`）、`frameInterval = 8ms`（`CameraAnimation` 的静态常量）、
工具条上的 `1.25`（`CanvasToolbar.zoomStepFactor`）。调一次手感要全项目搜索，
而搜索本身不可靠——`0.01` 这种数字到处都是。

现在全部收进 `MotionConfiguration.Feel`，每个字段都有真实消费者：

| 字段 | 消费者 | 改了会怎样 |
| --- | --- | --- |
| `panSpeed` | `MinimalInputAdapter.panDelta` | 直接乘在滚动位移上 |
| `mouseWheelLinesToPoints` | 同上（仅 `isPrecise == false` 时生效） | 鼠标滚轮的行→点换算。**当前 1，即不换算** |
| `magnifySensitivity` | `MinimalInputAdapter.magnify` | 捏合倍率 `1 + magnification × s` |
| `commandScrollZoomSensitivity` | `scrollWheel` 的 ⌘ 分支 | 每点滚动对应多少比例变化 |
| `zoomStepFactor` | `WorkspaceView` / `PinNativeApp`（4 处调用点） | 按钮与 `⌘=` 的步进比例 |
| `animationFrameInterval` | `CameraAnimation.init` | 程序化动画的帧间隔 |

三点值得说明：

1. **`mouseWheelLinesToPoints` 默认 1 是刻意的**，不是漏了。AppKit 对非精确设备
   给的是**行数**、对触控板给的是**点数**，两者差一个量级，批次 A 起两类都按点数
   处理——触控板是对的，鼠标滚轮会慢得几乎不动。**本机没有鼠标可实测**，凭猜给一个
   系数会把「手感已实机确认」这件事弄脏。接上鼠标时改这一个字段，不必回来改算式。
2. **`animationFrameInterval` 不是常量。** 它是实例属性、进循环前取出并捕获到局部，
   所以**动画播放到一半时改它不会影响正在播的那一次**——这是有意的语义，不是遗漏。
   构造函数里兜底 `max(0.001, …)`：0 或负数会让 `Task.sleep` 变成忙等
   （CPU 满载、风扇起飞），而参数可调之后这种输入迟早会出现。
3. **`viewportPreloadMargin` 仍然没有消费者**，它的文档里现在明写了这一点。
   没有顺手给它加几个"看起来配套"的字段：**B2 的迟滞参数必须和迟滞逻辑一起加**，
   先加字段就是制造下一个"接线了但其实没接"的陷阱（本批次已经踩过两次）。

### 二、越界是怎么发生的：`CALayer` 默认不裁剪子层

现象：合成素材里最左一列压在左侧面板的「还没有截图」空状态上，看起来像面板没渲染。

根因不是面板，是**画布**：`CanvasHostView` 是 `HStack` 里靠右的兄弟视图，
它的 backing layer **默认 `masksToBounds == false`**，世界坐标下超出视口的元素
照样被合成，于是画到了左边邻居身上。

三处选择：

- **裁在视口层，不裁 `worldLayer`。** `worldLayer` 带着相机变换，给它加蒙版等于
  **在世界坐标里裁**——跨越视口边界的元素会整块消失，而不是被切掉一半。
- **写 `init` 里，不写 `makeBackingLayer` 里。** 第一版就是写在
  `makeBackingLayer` 里的，**没有生效**：AppKit 拿到 backing layer 之后会把
  `masksToBounds` 重置为 `false`。用两个独立 `swiftc` 探针程序确认过。
- **它不是视口虚拟化。** 越界的图层仍然存在、仍然占内存、仍然在每帧被遍历，
  只是不再显示。真正的虚拟化是 B2。

### 三、这一轮断言怎么验的（缺陷注入实测）

| 注入的缺陷 | 变红的断言 |
| --- | --- |
| 把裁剪挪回 `makeBackingLayer`（即原 bug） | 1 条（画布图层裁剪到自己的边界） |
| `panDelta` 无视 `panSpeed` / 行→点换算 | 2 条 |
| 捏合灵敏度写死为 1 | 1 条（得到 1.1） |
| 帧间隔写死 8ms、无视配置 | 1 条（比值掉到 0.94） |
| **不注入**，直接跑 | 「帧间隔 200ms」自己红过一次，见下 |

### 四、两条断言本身写错了（第 3、4 条「没牙」）

前一批 B1 抓到两条**无论实现对错都通过**的断言；这一批抓到的是另一类问题：
**阈值画在了噪声的量级上**。

1. **「帧间隔 200ms：40ms 内几乎没推进」原本卡 `< 1%`，它自己红过一次——正好 1%。**
   原因不是代码：循环第一帧的 `elapsed` 是从 `CACurrentMediaTime()` 到 Task 真正
   被调度之间的那点延迟，**1ms 的延迟就对应约 3% 的推进**，1% 这条线和噪声同量级。
   现在改成比**同一时刻两侧推进量之比**（`快 > 慢 × 5`）：间隔被忽略时两侧必然
   几乎相等、比值掉到 1 附近；正常时约 145% 对个位数百分比。**比值是自归一化的**，
   机器整体忙闲不影响它。注入验证时它抓到的是 `慢 131% / 快 123%`——原来那条
   绝对值断言在这个注入下是绿的。
2. **「慢的那侧几乎没动」的初版断言的是"恰好不动"**，但循环是**先更新再睡**，
   第一帧必然已经前进一丁点。那是断言写错了，不是代码错了。

### 五、`cc-debug`：实测包不再覆盖正式包

演示素材（`DevelopmentCommands`）整个包在 `#if DEBUG` 里，所以"让人亲眼看一下
带素材的画布"只能用 debug 包——而它和 `cc` 用同一个输出路径，**实测一次就把正式包
覆盖掉了（已经发生过两次）**。现在 `scripts/build-app.sh debug cc-debug` 输出到
`build/Pin-cc-debug.app`，与 `build/Pin-cc.app` 并存，两者共用 `dev-cc` 数据目录
（bundle id 相同，它本来就是"同一个 Claude 工作区的实测包"）。
`release cc-debug` 直接拒绝：那种包名字叫"实测"却不含素材，以后一定会有人拿去实测。

### 六、快照从 7 张加到 8 张：补了一张"不套相机"的

原来那张有内容的快照调了 `camera.fit(...)`，把内容缩到视口里——**它永远看不见
"内容比视口宽"这件事**，而越界正好只在这种情况下发生。也就是说那份"图片显示正常"
的截图每天都在掩盖同一个 bug。

新加的 `workspace-overflow-1280x800-light.png` 不套相机（缩放 100%），**注入原 bug
后它如实复现了用户看到的现象**（素材盖住面板、吃掉「还没有截图」文案），是这条
修复的视觉回归证据。

## 画布是基底，素材面板与工具条浮在上面（产品负责人审核后返修）

产品负责人的原话是「整个面板以画布为基底，素材窗口作为一个悬浮层浮在画布上面，
且要用 SwiftUI 实现 liquid glass 效果，目前没有做到」。审核下来确实是五处没做到，
不是一处：

| # | 症状 | 成因 |
| --- | --- | --- |
| 1 | 画布被挤成"中间那一栏" | `HStack{来源栏, 面板, 画布}`——面板占了布局宽度 |
| 2 | 面板是一块实色 | `.background(DesignTokens.Surface.panel)`，与画布无关的纯色 |
| 3 | 面板不像浮起来的 | 直角、贴窗口左边、没有投影 |
| 4 | 空画布引导会被面板压住 | 它在左下角，而面板浮上来之后左下角正是面板的位置 |
| 5 | 工具条居中在错的地方 | 见下面第四节 |

### 一、结构：`HStack` 少了一栏

`MaterialPanel` 从 `HStack` 里挪进 `canvasArea.overlay(alignment: .leading)`，
画布于是拿到来源栏右侧的**全部**宽度，面板是画在它上面的一层。

这不是审美偏好，有一个能测的后果：**开关面板时画布尺寸不变**，相机不用重新适配，
视口里的内容不会跟着跳一下。第一版面板一动画布宽度就变，`camera.fit` 得重算。

来源栏没有跟着浮起来，保持实色贴边：它是导航不是浮层，而且贴着窗口边那一条
正是窗口的拖拽区。Pin Web 原型也是这么分的。

### 二、玻璃：`floatingPanelSurface()` 比 `glassSurface()` 多三件事

圆角裁剪、描边、投影，各有一条理由，写在 `UI/GlassSurface.swift` 的注释里。
其中**投影是"浮"这件事唯一的视觉依据**——没有投影就只是一块半透明色，
读起来仍然是分栏。原型用的也是 `0 8px 24px` 这一档。

裁剪只作用于面板内容：调整宽度的把手挂在裁剪**之后**，否则那半个越界的命中区
会被一起切掉，拖起来只有一半灵（原型 P0.3.1 踩过的坑）。

### 三、这一步最大的风险是"浮层会不会被画布吞掉"，只能测

画布是 AppKit 的 `NSView`，浮层是 SwiftUI 画在它上面的内容。AppKit 的命中测试
先看子视图，而**画布是真实子视图、浮层不是**——浮层完全可能被整个吞掉。
表现是"按钮点了没反应，画布反而平移了一下"，而截图上看不出任何异常
（浮层照常画在最上面）。读代码判断不了这件事。

实测结论：**不会吞**。`NSHostingView` 在命中测试里先问自己画的内容，落空才落到
representable 的 NSView 上。自检里 6 条断言把这件事钉住了（画布铺满、面板底下
是画布、面板拿得到点击、空白处仍命中画布、底部那一行有多少宽度可点、工具条居中）。

### 四、工具条居中：注释比代码更早地宣布了想要的结果

第一版把空画布引导挂在工具条右边，`HStack` 于是让工具条在"扣掉提示之后剩下的
空间"里居中。**实测 1280 宽、面板 240 时：工具条中心 688pt，画布中心 812pt**——
偏左 124pt，一眼看得出来。而当时的注释里写着「工具条居中在看得见的画布上」。

也就是说那条注释描述的是**想要的结果**，不是代码的行为。这种注释比没有注释更坏：
它会让下一个读代码的人跳过这一段去别处找问题。两个都改了。

修法是左边再放一份 `.hidden()` 的同款提示当**对称占位**，两边等宽，工具条就落在
行中心；占位用的是同一个视图，宽度不可能和右边那份走散。窄窗口放不下时由
`ViewThatFits` 整条丢掉提示——退让条件由 SwiftUI 按真实宽度算，
**原型那个"窄于 1050px 就藏起来"的魔法数字因此被替掉了**；它替不掉的是
"面板拖宽了还算不算数"，而这里"放不放得下"是当场量的。

### 五、两个注入实验的教训

- **"注入不红"不一定是断言没牙，也可能是注入根本没被调用。** 为了让"画布吞掉
  点击"变红，我重写了 `CanvasHostNSView.hitTest` 一律返回自己——6 条断言全绿，
  差点因此认定断言是摆设。实际原因是宿主视图先答自己画的内容，那个点根本轮不到
  画布那一层，重写它等于写了段死代码。换成**把浮层挂到 `.background`（压到画布
  后面）**，对应断言立刻红。**命中类的断言要注在层级上，别注在被命中的那一方身上。**
- **比值只是让阈值自归一化，不保证被量的东西不含噪声。** 「帧间隔控制节奏」那条
  断言经历了三版：绝对值（红）→ 比值（也红）→ 直接数帧数。第三版才对，因为
  前两版量的都是"40ms 那一刻推进了多少"，而节奏"慢"的那一侧 40ms 里只跑一帧，
  那一帧的 `elapsed` 就是 Task 被调度的延迟——**量到的其实是机器的忙闲**。
  数帧数之后慢侧的上界从"量出来的"变成"推出来的"（窗口比间隔短 ⇒ 最多一帧），
  与忙闲无关。计数器是个只服务自检的 `CanvasContext` 实现（`FrameCountingContext`），
  走的是和真实宿主相同的代码路径。

### 六、玻璃为什么拍不出来（这条决定了"谁说了算"）

`cacheDisplay` 离屏渲染**复现不了 Liquid Glass**：玻璃会渲染成一层很淡的半透明色，
没有背景模糊、也没有折射。于是 `--snapshot` 能证明的是**层级、几何、顺序**，
**不能**证明玻璃材质本身。

这条必须说清楚，否则那张截图会被当成"玻璃效果没问题"的证据。**玻璃的观感只能
在真窗口里看**：`build/Pin-cc-debug.app`（双击，带演示素材）。

### 七、已知边界：内容可能被面板压住一部分

面板浮在画布上之后，`focusContent` / `fit` 仍然按**整个视口**居中内容，
所以"定位内容"之后最左边那部分内容可能落在面板底下。遮挡感知的适配
（把面板宽度算进可视区域）没有做——它属于缩放入口的语义变更，
不是这次结构调整的一部分，先记在这里。

## 像素需求的三条路径（独立复审报回两条 P1 之后的返修）

复审在隔离副本里补了真实路径的回归测试，**287 项中 2 项失败**，两条都成立，
都在图片管线里，都是"某个输入变了、而它该触发的重算没接上线"。

### 一、`renderer.camera` 写了，档位没重算

捏合、⌘+滚轮、拖拽平移、工具条缓动——**这些都不走 `apply`**，它们直接写
`context.camera`（见 `MinimalInputAdapter`）。而重算档位当时挂在渲染增量那条路上
（`apply` 与 `updateLayerFrames`），两条路不是同一条。表现是**放大之后画面停在
低清档**：矩阵是更新了的，所以代码读起来正常、截图也看不出异常。

修法不是在每个调用点补一句，而是**把重算挂到相机属性本身**：

```swift
var camera: CanvasCamera {
    get { storedCamera }
    set { adoptCamera(newValue, recomputeTiers: true) }
}
```

这样"写相机就一定重算"是结构保证的，将来谁再加一条改相机的路径也不会漏。
`apply` 那条用 `adoptCamera(_, recomputeTiers: false)`：它开头的相机赋值发生在
元素外框更新**之前**，那时重算会拿旧外框算出一个中间档位、白跑一次解码，所以
它留到图层都改完再统一重算一次。

### 二、换素材而档位没变时，画面继续显示旧图

`requestImage` 当时只比档位（`displayedTier[id] != tier`）。档位是"多少像素"、
素材是"哪张图"——**两个都会变的东西只比了一个**。同一个元素换了素材、而新素材
在同一档位上时，它判定"没变化"，于是旧图留在图层里，而所有记账看起来都是对的。

改成 `DisplayedImage { asset, tier }` 一起比。两个合成素材特意选得"同档不同像素"
（3840×2160 与 3456×2234 在 400pt 宽、2× 屏下都落在 1/4 档，但解出来是 960×540
与 864×558），断言读图层里的实际像素尺寸，所以它分辨得出"换了"和"没换"。

### 三、我自查同一类缺陷，又找到第三条

`setBackingScaleFactor` 只把图层的 `contentsScale` 改了，**没有重算档位**——
从 1× 屏拖到 2× 屏之后，图层按 2× 画一份 1× 的像素。复审没报这条（它需要换显示器
才看得见），但它和上面两条是同一个缺陷类。

于是把不变量写清楚：**一个元素需要多少像素，只有三个来源——元素外框、相机缩放、
屏幕倍率。** 三个各有且只有一个触发点：

| 来源 | 触发点 |
| --- | --- |
| 元素外框 | `updateLayers` / `insertLayers` |
| 相机缩放 | `camera` 的 setter |
| 屏幕倍率 | `setBackingScaleFactor` |

`updateLayerFrames` 里原本也有一句 `refreshImageTiers()`，注释写着"视口变大 =
元素在屏幕上变大 = 可能该换更细的一档"——**那句话是错的**（把"窗口变大"当成了
"缩放变大"），而且那行代码从来没有改变过任何一个档位：视口尺寸不在三个来源里。
错的注释和没用的调用一起删掉，原地留下上面这张表。

这是本项目第三次出现"注释比代码更早地宣布了想要的结果"（前两次：工具条居中、
`makeBackingLayer` 里的裁剪）。三次的共同点都是**注释描述的是意图，而代码在做
另一件事**，而两者都没有东西钉住。

### 四、`addBoard(named:)` 与 `rename` 的名字规则分家了

复审列为非阻断项，一并修了：`rename` 挡空白名，`addBoard` 却收下，于是一块名字是
空白的画布进了列表。规则收进同一处 `normalizedName(_:)`（去首尾空白、不许空），
区别只在空白时怎么办——新建时**回落到默认名**而不是拒绝：新建这件事必须发生
（调用方还会切过去），拒绝只会留下"点了新建却什么都没发生"。

### 五、这一轮断言怎么验的

四条断言**在修复之前**先跑红，红项与复审的描述逐字一致（缓动放大后仍是 960×540、
捏合后仍是 960×540、屏幕倍率变了仍是 960×540、换素材后仍是旧图的 960×540）——
修复前的运行本身就是注入证据，这比事后注入更硬。`addBoard` 那两条与
"平移不重复发请求"用注入复验，**各转红 2 条**：把 `addBoard` 改回原始 `name`，
红出「空白名字不会被原样收下」与「新建时去掉首尾空白」；去掉 `requestImage` 里
`displayed[id] != wanted` 那句，红出「档位没变时不重复发请求」（1 → 2 次）与
「平移不重复发请求」（18 → 19 次）。注入的代码都已还原，还原后 299/299。

**又抓到自己写的一条瞎断言**：第一版把"图层里的像素"和**渲染器自己记的档位**比，
缺陷还在时它照样绿——期望值取自被测方自己的账，等于自证。改成独立算一遍
（`demandedPixelSize`）之后才红。同理，三段路径的落点**特意各要求一个与上一段
不同的档位**：落点若恰好与上一段同档，缺陷还在时那条也是绿的（画面里本来就是
那一档的像素），等于没有牙。

### 六、这一轮修法自己的代价

重算挂到相机 setter 之后，**拖拽平移的每一帧也会走一遍档位扫描**（平移也是写相机）。
O(元素数) 的字典扫描在 O(10²) 量级是几十微秒（**这是估算，不是测量值**——
本轮没有测耗时，性能口径按 §2.4 属 B2 报告），与 §2.4 的 8ms 主线程预算差两个数量级，
但"每帧重发请求"就不一样了——所以补了一条断言钉住"重算 ≠ 重发"：平移之后请求
次数不许涨。**没有**按"只有 zoom 变了才重算"去省这一次扫描：档位的依据是"需要
多少像素"，而这句话将来可能不止看缩放（B2 的预加载边距就带着视口概念），
省几十微秒换回一类静默缺陷不划算。

## 批次 B2：虚拟化、迟滞、缓存预算、取消、性能实测

路线图 §2.4 与 §3 的六件事。**送审清单在 `CODEX_REVIEW_REQUEST.md`**（逐文件改动、
五次注入的红项、六个判断、未验证清单）；**实测数字在 `PERF_REPORT_B2.md`**。
这一节只写"为什么是这么做的"和"踩到了什么"。

### 一、场景里的元素 ≠ 有图层的元素

B1 的渲染器给**每个**元素建 `CALayer`——1000 个元素就是 1000 个图层，屏幕外的
照样合成、照样占内存。B2 把它拆成两张表：

| 表 | 管什么 |
| --- | --- |
| `elementModels` | 场景里的**全部**元素（外框、素材 ID、层次） |
| `elementLayers` | **当前有图层**的那些——只有可见区（外扩一个预加载边距）内的 |

`refreshVisibleContent()` 是唯一的入口：算一次可见世界矩形（视口 ÷ 缩放，再按
`viewport.preloadMargin` 外扩），然后建/撤图层。**撤层时同时取消在飞的解码**
——这是取消的触发点（见四）。

丢的是**图层与像素**，不是元素：命中测试、外框、删除都照旧走 `elementModels`。
所以虚拟化省的是内存与解码，不是场景规模——这一点在复审时容易被误解。

**预加载边距为什么是 256 点**：它是"拖出去一屏才开始解码"的提前量。太小则快速
平移时空白跟着光标跑，太大则虚拟化省不下东西。**这个数没有实测依据**，是拍的；
报告第 4.1 / 4.2 节量到"300 与 1000 元素平移时建层峰值都是 28"，说明这个量级下它是够的。

### 二、迟滞做成纯函数，而且只在降级侧有旋钮

`LODTier.settled(_:original:from:headroom:)` 是**纯函数**，不是在渲染器里写条件：
迟滞最容易出的错是"某个方向上永远换不了档"，而那种状态只有真实的缩放序列才碰得到
——在画布上捏合几十次也未必撞上，撞上了也只是觉得"有点糊"。做成纯函数就能把整条
轨迹（来回抖、单向大跨步、反复跨边界）在自检里直接喂进去跑完。

规则一句话：**升级立刻（就是 `fitting`），降级要求下一档在加 1.414 倍余量之后仍然
够覆盖需求**。旋钮只给降级侧，因为两个方向的成本不对称——升级慢了是"糊"（用户
立刻看得见），降级急了是"重解"（只在快速来回缩放时看得见）。代价是需求快速**上行**
时仍会立刻换档；抖动之所以被止住，是因为抖动要跨边界必须先降级，而那一侧有余量。

`settled` 的 `from:` 传的是**当前已经显示或已经发出请求的那一档**。传 `nil` 时它
退化成 `fitting`——这正是"这个元素刚进视口、没有上一档"的情形。

### 三、缓存预算：512 MB 这个数从哪来，以及它在什么情况下不够

一张 4K 解码后 3840×2160×4B ≈ 31.6 MB。路线图 §2.4 要测「20 张不同的 4K 图」，
全按原分辨率留着就是 **632.8 MB**——所以预算不能拍脑袋定大，LOD 必须真的在省内存。
默认取物理内存的 1/8，夹在 64 MB ~ 512 MB 之间（本机 24 GB → 512 MB）。

**实测到了这个预算的边界**：20 张 4K 全尺寸是 632.8 MB > 预算。工作集大于预算时，
LRU 加一路向前的扫描会退化成**反复重解**——刚解好的那张，在走到它之前就被后面的
挤掉了。报告第 4.4 节 ③ 实测：回到 200% 再走一遍，20 张里重解 **19 张**。
**这不是实现错误，是"缓存放不下整个工作集"的必然结果**；它说明 512 MB 在
"20 张 4K 全尺寸"这个场景下不够，属于**待决的参数**，不是可以顺手改掉的 bug。
调大只是把同一个问题推到 40 张。

另一条：**单张比预算还大时不把它自己淘汰掉**——否则每次重绘都要重新解码，
比多占几十兆糟得多。内存压力压到下限（64 MB）也是同一个判断。

内存压力的响应（`ImageCache.handle`）是**单向**的：warning 减半、critical 减到
下限，压力消失也不长回去。理由是没有可靠的"可以长回去"的信号，而错误的长回去要
在下一次压力时才暴露。订阅在 `MemoryPressureMonitor`（`DispatchSource`），
**它和缓存分开**：压力是系统事件，"收到压力怎么办"才是缓存的事。

### 四、取消的判据在**解码开始之前**

`SyntheticImageProvider` 检查取消的时机是拿到 in-flight 任务之后、真正解码之前：
**已经开始的解码不打断**。理由是那一份像素可能马上又被需要（用户来回拖），打断
意味着半途而废再重来；"还没开始的"没有任何浪费。

于是口径是：**取消数 = 在解码开始前被顶掉的请求数，这些解码没有发生**，
报告里的"取消 N 次"就是这个意思。"省下的时间"是这一部分的，不是"打断在途解码"的。

### 五、埋点默认关，而且这件事本身有断言

`PerformanceProbe.isEnabled` 默认 `false`，只有 `--perf-report` 打开。自检跑完
380 条之后断言探针**一个耗时样本、一个计数都没记**——因为埋点一旦默认开就是常驻
开销，而且"报告里的数字变慢了"会分不清是产品慢了还是埋点慢了。

`measure` / `count` 收 `StaticString`：`OSSignposter.beginInterval` 要求它
（signpost 名字要能静态注册）。**接口跟着系统约束走**，没有为了让调用点好看而
包一层——包一层就等于把那个约束藏起来，下一个调用点会以为可以传变量。

### 六、§2.4 的报告是**每帧主线程工作耗时**，不是帧率

`--perf-report` 和 `--snapshot`、`--selftest` 同构：在 `PinNativeApp` 之前退出、
**不开窗口**。所以：

- `CATransaction.commit()` 只是把图层改动写进渲染树，真正的合成、显示链路与垂直
  同步在 WindowServer 里——**这里量不到**。每一个数都是主线程工作耗时。
- 图片解码不在主线程，所以解码耗时不出现在任何一栏；它的代价只体现在
  "首扫 vs 回扫"的差异上。
- 玻璃面板常开，但材质合成在系统侧，离屏量不到。
- 素材是合成的（平面色块 + 细线），真实照片的像素熵高得多——**合成素材偏乐观**。

**帧率与真机手感要人工跑一次 Instruments**（signpost 已接好：subsystem
`com.pin.native.canvas`，category `PointsOfInterest`）。**本报告不代表那一步做过。**

### 七、B2 断言怎么验的（缺陷注入实测）

| 注入的缺陷 | 变红的断言 |
| --- | --- |
| 可见性判据改成恒真（所有元素都建层） | 9 条 |
| 渲染器调用点把迟滞余量写死成 1（即 B1 行为） | 1 条（「缩到 2/3 倍时档位不动」） |
| `evictIfNeeded` 直接返回 | 4 条 |
| 撤层时不取消在飞的解码 | 2 条 |
| 内存压力不收缩预算 | 4 条 |

五组共 20 条红项，逐条的原文在 `CODEX_REVIEW_REQUEST.md` §3。还原后重建
0 error 0 warning、380/380。

三处值得单独记的：

- **迟滞那条只有 1 条红是对的**：迟滞只有降级侧有旋钮，而这条落在**渲染器的调用点**
  上——纯函数那一组（15 条）证明不了"渲染器用的是配置里那个余量"。
- **缓存那一组有两条"守一下"型断言**（"这张图确实撑爆了预算"）。没有它，第一条
  「超预算时淘汰最久未用的」在"根本不记账"的实现下也是绿的。

### 八、B2 踩到的坑（前四条会直接误导审核）

1. **换一块显示器，同一份代码的档位差一级。** `NSScreen.main?.backingScaleFactor ?? 2`
   乘进像素需求，于是 1080p@1× 与内置 Retina@2× 上 `fitting` 的结果不同。我先按
   "这是 bug"查了两轮，最后靠 `grep 显示器` 对比两次运行的表头才定位。
   **报告表头那行「屏幕倍率」是必须核对的字段**；两次运行的档位不可比就是这个原因。
2. **`phys_footprint` / `resident_size` 看不见未被触碰的 purgeable 页**，而
   CoreGraphics 位图上下文的字节正是这么分配的。实测：16 张 4K 的 `CGImage` 刚建好
   时 footprint 只涨 2 MB，把每张画一次之后涨到 509 MB（账面 506 MB）；对照实验里
   一次普通的 512 MB `malloc` 写入**看得见**（+513 MB）。所以"内存涨没涨"不能只问
   footprint——报告里每一处都同时给"账面"和"读写之后"两栏。
3. **迟滞的收敛会被"扫描时机"骗。** 量收敛的第一版只 `drain` 一次就宣布"1 轮扫描后
   停住"，报的是 1/2；真实稳定点是 1/4。原因是降级每轮只走一级，而**扫描只在相机
   写入与解码完成时触发——空闲不会自己收敛**。改法是每次轻推相机 1 个世界单位强制
   一次扫描，并要求连续两轮不变才算收敛。
4. **测量台自己的输出也会有"看起来像 bug"的样子。** 报告里每个 pass 的缓存统计行
   打印在它自己的标题**之上**（`sweep` 先打印、`report(sweep:)` 后打印标题），我把
   冷扫那一行读成 0 命中，差点判定 `clearCacheFirst` 是坏的。实际是排版错位，
   代码没错——改成把统计装进 `SweepResult` 再统一打印。
5. **迟滞必须有一条"该降就降"的反向断言**：只有"不降档"那一条的话，"永远不降档"
   的实现在断言上完全通过，而那是比抖动更糟的缺陷。
6. **落点压在档位边界上的断言等于没验**：反向断言的第一版缩到 0.4 倍，需求正好是
   480（1/8 档的宽度），浮点误差让"刚好覆盖需求"在相邻两档之间跳，缺陷因此藏住了。
   改成 1/3 倍（需求 400，离两侧边界都有两成余量）才有效。
7. **两张内容快照不可逐字节比对**：`SyntheticImageProvider.makeAssets` 里是
   `Asset(id: AssetID(), …)`——**每个进程一份新 UUID**，而合成图的噪声种子由它派生，
   所以每次跑出来的画面内容本来就不同（同一二进制连跑两次，像素流就不一样）。
   B2 重拍快照时我先按"内容变了=渲染变了"查了一轮，最后靠 `makeUniform4KAssets`
   的调用点与 `seed(from:)` 对上才确认是素材本身随机。
   **空画布那 6 张是逐字节稳定的**（B1 → B2 一字不差），它们仍可做回归证据；
   两张内容图只能靠眼睛看。要让内容快照也能逐字节比对，得先把演示素材的 ID 确定化，
   并且确认档位已收敛之后再拍——**那是下一轮的事**，本轮没改（改了也只解决一半：
   解码完成的时序仍会影响那一刻停在哪一档）。

### 九、B2 之后还剩什么

- **扫描是 O(场景元素)**，不是 O(可见元素)——`refreshVisibleContent` 遍历整个
  `elementModels`。1000 元素下 P99 0.411 ms，离 8ms 预算还有二十倍，所以**没有**
  改成空间索引（那要连"索引与元素框更新的一致性由哪条断言钉住"一起设计）。
- **预加载边距 256 点没有实测依据**（见一）。
- **512 MB 预算在 20 张 4K 全尺寸下不够**（见三）——待决的参数。
- **真实系统内存压力没测过**：报告第 4.6 节那份压力序列是**构造的**。
- 遮挡感知的适配仍未做（`focusContent` / `fit` 按整个视口居中）。

## 已知限制与风险

1. **默认启动仍是空白画布**（产品行为，§6）。图片管线已经通了，但画布上的内容
   只能靠调试菜单（`⌘⇧D`）放进去——真正的导入属于批次 C。release 构建里没有
   这个菜单，所以 release 的快照是 6 张空画布，**"图片管线是通的"这条证据只在
   debug 构建里存在**。
2. 相机手感已由用户实机确认（2026-09-16），但**元素本身的拖动与缩放没有验证过**——
   输入通道就绪、入口为空，元素级交互属于批次 C。
3. 输入只有平移、捏合、拖拽、按钮缩放、定位内容。选择 / 框选 / 多选 / 元素拖拽 /
   快捷键的**通道已就绪但入口为空**（`MinimalInputAdapter` 里对应方法留了空实现
   并注明属于批次 B）。
4. 覆盖层通道通了，但**不绘制**——`LayerRenderer` 只把 `CanvasOverlay` 存下来。
   选择框与手柄的画法要和选择模型一起定。
5. 素材面板与来源栏只有外壳；**素材读取、导入、拖拽属于批次 C**。本轮把面板改成了
   由 `MaterialProvider` 驱动，但提供者仍是占位实现（恒返回空列表），
   面板里那份条目列表渲染也**没有经过真实素材的验证**——没有素材库可读。
   批次 C 接手时请把它当成待重做的占位形态，参考它的只有状态机那一层。
6. **多画布没有界面**，也没有持久化。`BoardStore` 的管理操作可用且被断言覆盖，
   但用户看不到、也点不到；重启后只有初始的那一块画布。完整管理按 §6 属于后续阶段。
   另外**画布名字目前只存在于内存**，`Board.createdAt` 也还没有任何消费者。
7. 菜单弹出（右键菜单）未接，见上文「已知边界」。
8. 临时实现两处，均在文件头注明，可整体删除：
   `Canvas/MinimalInputAdapter.swift`、其中的 `CameraAnimation`。

## 开发中踩到、值得你知道的坑

1. **`glassEffect` 会让容器最外侧的子视图变白。** 工具条最左（定位内容）和最右（面板开关）
   两个按钮在浅色模式下直接消失，中间的放大镜完好——同一段代码只差位置。
   修法是把玻璃放进 `.background`，让它当背景而不是滤镜。详见 `UI/GlassSurface.swift`。
2. **`Timer` 的 block 是 `@Sendable` 且非隔离**，在里面碰主 actor 状态会报
   `sending ... risks causing data races`。主 actor 上跑 `Task` 循环更省事。
3. **`CanvasCamera.worldToView(.zero)` 有歧义**——`CGPoint` 与 `CGRect` 两个重载
   都有 `.zero`。要写 `CGPoint.zero`。
4. **SF Symbols 的 `textformat` 系列在中文系统下整族都是汉字。** `textformat` →「格式」、
   `textformat.size` →「大小」、`textformat.abc` →「甲乙丙」，来源栏上就成了
   「格式」标签配「字体」功能。`textformat.alt` 也一样。
   `.environment(\.locale, Locale(identifier: "en_US"))` 能强制回拉丁字形（实测有效），
   但那是靠环境值传播生效的，哪天不传播了就悄悄退回汉字。现在用 `a.square`：
   拉丁字母 A 加方框，**结构上不可能被本地化**。
5. **CALayer 的隐式动画会让拖拽"发黏"。** 默认 0.25 秒的 position/bounds 过渡会让
   图层追光标，看起来像手感问题，实际是插值。元素图层建的时候就要挂上
   `layer.actions`（全 `NSNull`）。
6. **`.build/debug/` 与 `.build/arm64-apple-macosx/debug/` 深度不同**，
   靠数路径层级找输出目录会错位。往上找含 `Package.swift` 的目录更稳。
7. **`Thread.isMainThread` 在 async 上下文里是 `unavailable`**（Foundation 标的：
   在 async 里问"我在不在主线程"通常是写法有问题）。但我们要问的这个问题是正当的
   ——"解码有没有意外留在主线程"——所以直接落到 C：`pthread_main_np() != 0`。
   绕过去这件事在代码里注明了理由，不是随手绕过。
8. **`Any?` 往 CoreFoundation 类型做条件转换，编译器判成"永远成功"（是 error 不是
   warning）**：`contents as? CGImage` 和 `contents as AnyObject as? CGImage` 都不行。
   类型判断要走 `CFGetTypeID(contents as CFTypeRef) == CGImage.typeID`。
   这在读 `CALayer.contents` 时必踩——而那个判断不能省：省了就等于"图层里放什么
   都算对"，以后有人放了 `NSImage` 也照样通过。
9. **`#if DEBUG` 里的类型在 release 里不存在**，引用它的代码会编译失败——
   而失败位置在**引用处**，不在定义处，容易看着莫名。`SnapshotHarness` 就是因此
   把内容快照整块包进 `#if DEBUG` 的。签名分叉（release 少一个参数）不要做：
   那会让调用点也跟着分叉。
10. **只按一个轴选档位会把细长图拉糊。** 4000×1000 的图要 900×400 的像素时，
    只看宽度会选到 1/4 档（1000 宽），高度只剩 250——不够。断言里专门有一条
    钉这个（注入"只看宽度"后它变红）。

11. **`CALayer` 默认不裁剪子层，画布会画到兄弟视图上。** `CanvasHostView` 是
    `HStack` 里靠右的兄弟视图，超出视口的元素照样合成，于是压到左侧素材面板上
    （用户实测发现）。而且 **AppKit 会在 `makeBackingLayer()` 返回之后把
    `masksToBounds` 重置为 `false`**——第一版就写在那里，看起来完全合理，实测不生效。
    要用 `swiftc` 写个两行的探针程序确认，别靠读代码判断（见 `CanvasHostView.init`）。
12. **不要把断言的阈值画在噪声的量级上——而"改成比值"并不自动解决这件事。**
    这条断言经历了三版才对，值得整条读完：
    - 第一版「40ms 内推进 < 1%」自己红过一次，红的不是代码是阈值：循环第一帧的
      `elapsed` 含 Task 调度延迟，1ms 就对应约 3% 推进。
    - 第二版改成**比值**（快/慢），以为自归一化就稳了。没有：节奏"慢"的那一侧
      40ms 里只跑一帧，那一帧的 `elapsed` **就是**调度延迟，所以慢侧量到的仍然
      是机器的忙闲。它第三天又红了（慢 40% / 快 143%，比值 3.6 < 5）。
    - 第三版改成**直接数帧数**才对：慢侧的上界从"量出来的"变成"推出来的"
      （窗口比间隔短 ⇒ 最多一帧），与忙闲无关。
    结论：拿时间做断言之前，先问「这个数是被什么决定的」——如果答案里有"调度"
    或"负载"，换一个能被结构决定的量。
13. **"注入缺陷后断言没红"有两种解读：断言瞎了，或者注入根本没被调用。**
    为验证"浮层会不会被画布吞掉"，我重写 `CanvasHostNSView.hitTest` 一律返回自己，
    6 条断言全绿。差点据此认定断言是摆设。真实原因是 `NSHostingView` 先答自己画的
    内容，那个点轮不到画布那层，重写它等于写了段死代码。换成把浮层挂到 `.background`
    （压到画布后面），对应断言立刻红。
    **命中类断言要注在层级上，别注在被命中的那一方身上。**
14. **`cacheDisplay` 拍不出 Liquid Glass。** 离屏渲染里玻璃只是一层很淡的半透明色，
    没有背景模糊也没有折射。所以快照能证明**层级、几何、顺序**，不能证明材质——
    "玻璃好看不好看"只能在真窗口里判断。别让一张拍不出材质的截图充当它的证据。
15. **注释会描述"想要的结果"而不是代码的行为，而且它比代码更早地宣布。**
    `bottomRow` 的注释写着「工具条居中在看得见的画布上」，实测中心差 124pt。
    这类注释比没有注释更坏：读代码的人会相信它，然后去别处找问题。
    **写完注释回头量一次**，尤其是注释里出现"正好""居中""不会"这类词的时候。
16. **期望值取自被测方自己的账，断言就是自证的。** 上一轮我写了「捏合后图层的像素
    换成了新档位」，但对照的是渲染器自己记下来的档位——**缺陷还在时它照样绿**，
    因为两边都是同一份错的账。改法是独立算一遍（`demandedPixelSize`），然后读
    图层里**实际的** `contents` 尺寸。判据只要有一次取自被测方的记录，那条断言
    对"被测方记错了"这一类缺陷就永远是绿的，而这一类恰好是图片管线里最常见的一类。
17. **测试块的落点如果和上一段同档，它也没有牙。** "三段路径各自触发重算"的第一版
    里，第三段的终点恰好回到第二段已有的档位——缺陷还在时画面里本来就是那一档的
    像素，断言全绿。**每一段的落点必须要求一个与上一段不同的档位**，否则"变了"
    和"没变"在图层里长得一样。
18. **`phys_footprint` / `resident_size` 看不见未被触碰的 purgeable 页**，而
    CoreGraphics 位图上下文的字节正是这么分配的（B2 实测：16 张 4K 刚建好只涨
    2 MB，逐张画一次后 509 MB）。所以"内存涨没涨"**不能只问 footprint**——
    要么先把像素读写一遍，要么用账面。用 footprint 下结论会得出"缓存不占内存"。
19. **时间戳/显示器之类的表头字段不是装饰。** B2 同一份代码在 1080p@1× 与
    Retina@2× 上档位差一级（`backingScaleFactor` 乘进像素需求），我按 bug 查了
    两轮才发现是环境差异。**两次实测的档位不可比之前，先比环境。**
20. **"空闲一会儿就收敛"是错的假设。** 迟滞的降级每轮只走一级，而重算只在
    相机写入与解码完成时触发——空闲不会自己收敛（B2 第一版量收敛只 drain 一次，
    报的是 1/2，真实稳定点是 1/4）。**量一个会收敛的量之前，先问它靠什么推进。**
