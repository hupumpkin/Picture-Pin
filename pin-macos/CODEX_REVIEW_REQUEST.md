| 注入 | 改法 | 红项 |

| ① 视口虚拟化失效 | `refreshVisibleContent` 里的可见性判据改成恒真（所有元素都建层） | **9 条** |

五次注入后全部还原，重新构建 **0 error 0 warning**，`--selftest` **380/380**。

三条值得单独说的：

1. **② 只有 1 条红，而它是对的。** 迟滞的两个方向里只有降级侧有旋钮，所以注入只
   影响降级。而这 1 条落在**渲染器的调用点**上——纯函数那一组（15 条）证明不了
   "渲染器用的是配置里那个余量"。这条就是那个证据。
2. **③ 的第 3、4 条是"守一下"型断言。** 第 1 条（超预算时淘汰）在"根本没记账"的
   实现下也会绿——存了多少记多少，永远不会超。所以先钉住"这张图确实撑爆了预算"，

3. **④ 与 ① 有一条重叠**（都报「移出视口也取消了在飞的解码」）。这是刻意的：
   取消的触发点是虚拟化撤层，所以任何一侧坏掉它都该红。

## 4. 六个判断（都可以质疑）

### 4.1 512 MB 预算在「20 张 4K 全尺寸」下不够——这是**待决的参数**，不是 bug

20 张 4K 全尺寸是 632.8 MB，预算是 512 MB。工作集大于预算时，LRU 加上一路向前的
扫描会退化成**反复重解**：实测回到 200% 再走一遍，20 张里重解了 **19 张**。

**我没有去把预算调大。** 调大只是把同一个问题推到 40 张，而路线图 §2.4 要的正是
"20 张不同的 4K 图"这个场景——这个数字本身就是拿来暴露参数的。真正的解法是策略
（例如视口外的元素不留全尺寸像素），那是另一个决定。**请你就这个参数给意见**：
512 MB 是留、是改，还是改成"按可见元素数动态算"。

### 4.2 内存压力的预算收缩是**单向**的，压力消失也不长回去

`ImageCache.handle(_:)` 收到 `warning` 减半、`critical` 减到下限（64 MB），
**没有任何路径把预算调回**。理由是长回去的时机没有可靠信号（"压力回到正常"不等于
"现在可以多占"），而错误的长回去要在下一次压力时才暴露。代价是：一台机器只要报过
一次 warning，这次运行就一直在半预算下跑。**如果你认为该有恢复路径，请说**——
那需要一个可证的判据，不能是"过一会儿再试试"。

### 4.3 取消的判据放在**解码开始之前**，不是中途打断

`SyntheticImageProvider` 检查取消的时机是拿到 in-flight 任务之后、真正解码之前。
已经开始的解码**不打断**——理由：那一份像素可能马上又被需要（用户来回拖），
打断意味着半途而废再重来；而"还没开始的"没有任何浪费。

于是报告里的口径是：**取消数 = 在解码开始前被顶掉的请求数，这些解码没有发生**。
"省下的时间"是这一部分的，不是"打断在途解码"的。

### 4.4 埋点默认关，且默认关这件事本身有断言

`PerformanceProbe.isEnabled` 默认 `false`；自检跑完 380 条之后断言探针
**一个耗时样本、一个计数都没记**。理由：埋点一旦默认开，桌面应用里就是常驻开销，
而且"报告里的数字变慢了"会分不清是产品慢了还是埋点慢了。

`measure` / `count` 收 `StaticString` 不是洁癖：`OSSignposter.beginInterval` 要求
`StaticString`（signpost 的名字要能静态注册）。**接口跟着系统约束走**，不为了让调用
点好看而包一层。

### 4.5 虚拟化筛的是元素，但**扫描仍是 O(场景元素)**——这条是实测发现的

`refreshVisibleContent()` 是 `for (id, element) in elementModels { if element.frame.intersects(rect) … }`
——遍历**整个场景**，不是遍历可见元素。报告里量到的证据：300 → 1000 元素（3.3×）
时扫描中位数 0.050 → 0.142 ms（2.8×），而两种元素数下建层峰值都是 28。

**我没有顺手改成空间索引。** 1000 元素下 P99 是 0.411 ms，离 §2.4 的 8ms 主线程
预算还有二十倍；现在加索引是拿一个真实的复杂度换一个不需要的性能。
你复审时如果认为该加，请说——但请连"索引与元素框更新的一致性由哪条断言钉住"
一起提，否则它会变成下一个静默缺陷。

### 4.6 迟滞只加在**降级**侧，升级侧没有旋钮

需求一涨过当前档就换细，与 `fitting` 完全一致（断言里直接比对了这两者）。
理由：升级慢了下场是"糊"，那是用户立刻看得见的；降级急了下场是"重解"，只在快速
来回缩放时才看得见。**两个方向的成本不对称，所以旋钮也只给一侧。**

代价写在这里：需求在边界上快速**上行**时仍会立刻换档。这不是遗漏——抖动之所以
被止住，是因为抖动要跨过边界就必须先降级，而那一侧有 1.414 的余量（报告第 4.5 节
实测：有迟滞换档 **0** 次，无迟滞 **192** 次）。

## 5. 实测数字 → `PERF_REPORT_B2.md`

报告的结论摘要（**完整口径、每一条的测量方式与反例都在报告里**，不在本清单重复）：

| 项 | 实测 | §2.4 目标 |
| --- | --- | --- |
| 启动（进程入口 → AppKit 就绪 + 画布建立） | **87.0 ms** | < 800 ms |
| 每帧主线程工作 P95（1000 元素平移，首扫） | **0.312 ms** | < 8 ms |
| 每帧主线程工作 P95（1000 元素全可见，上限对照） | **0.586 ms** | < 8 ms |
| 建层峰值（1000 元素，视口虚拟化下） | **28 个** | — |
| 20 张 4K 峰值 / 稳定 / 淘汰后 | **541.8 / 488.5 / 506.2 MB** | — |
| 档位边界抖动 ±2% × 24 次 | 换档 **0** 次（无迟滞：192 次） | — |

**这些不是帧率**，是每帧主线程工作耗时。报告第 5.1 节列了 8 条口径限制，其中最要紧的

与垂直同步在 WindowServer 里，这里量不到。

   从 1× 屏拖到 2× 屏的真实行为仍未实机验证（本机只有一块屏）。
4. **真实系统内存压力：造不出来。** 报告第 4.6 节那份压力序列是**构造的**，
   调的是 `ImageCache.handle` 这个产品入口。真实压力下 `DispatchSource` 的
   投递行为、以及与系统回收的互动，没有测过。
5. **鼠标滚轮的系数仍未归一化**（B1 遗留，未变）：本机没有鼠标可实测。
6. **面板拖宽时工具条跟着动、`⌘⇧B` 换画布的手感**：前者是产品判断，后者有断言钉
   "不重解码"但没有手感判断。均待人工确认。
7. **报告里的素材是合成的**（平面色块 + 细线），真实照片的像素熵高得多，
   解码耗时与内存都受这一点影响——**合成素材偏乐观**。
8. **边界抖动不能在自检里断言**：它要的是一条真实的"需求贴着边界来回走"的时间
   序列，而 `LODTier.settled` 是纯函数——报告第 4.5 节那条轨迹是测量台自己走的，
   不是自检覆盖的。**它是证据，不是回归防护。**

## 7. 已知边界

- **扫描是 O(场景元素)**，不是 O(可见元素)——见 §4.5。1000 元素下 P99 0.411 ms。
- **工作集 > 预算时会反复重解**——见 §4.1，19/20 张。
- **视口虚拟化丢的是图层，不是元素**：元素模型、外框、命中测试全都还在，
  只有 `CALayer` 与像素被丢掉。所以它省的是内存与解码，不是场景规模。
- **玻璃面板常开**（`UI/GlassSurface.swift` 没有开关），报告是离屏的，量不到材质合成。
- **越界图层裁剪是 B1 的修复，不是虚拟化**：这两件事容易混。裁剪管"画到兄弟视图上"，
  虚拟化管"视口外的元素占不占内存"。
- 遮挡感知的适配仍未做（`focusContent` / `fit` 按整个视口居中，内容最左边可能落在
  面板底下）。

它每次跑都会打印时间戳与当前显示器——**和你手上那份 `PERF_REPORT_B2.md` 对不上
时间或显示器是正常的**，但**档位、层数、缓存统计这些结构性数字应当能对上**；
对不上就是环境差异，先看报告第 2 节（环境）表头里的「屏幕倍率」（见 §6.3）。

注入回归想自己复现的话：把 `LayerRenderer` 里 `refreshVisibleContent` 的可见性
判据改成恒真，应当红 9 条；把渲染器调用点的 `headroom` 写死成 1，应当红 1 条
（「缩到 2/3 倍时档位不动」）。

## 9. 这一轮踩到的坑（写下来是因为它们会误导审核）

1. **换一块显示器，同一份代码的档位差一级。** `NSScreen.main?.backingScaleFactor ?? 2`
   乘进像素需求，于是 1080p@1× 与 Retina@2× 上 `fitting` 的结果不同。我先按"这是
   bug"查了两轮，最后靠 `grep 显示器` 对比两次运行的报告表头才定位。**报告第 2 节那行「屏幕倍率」是必须核对的字段**，不是装饰。
2. **`phys_footprint` / `resident_size` 看不见未被触碰的 purgeable 页**，而
   CoreGraphics 位图上下文的字节正是这么分配的。实测：16 张 4K 的 `CGImage` 刚建好
   时 footprint 只涨 2 MB，把每张画一次之后涨到 509 MB（账面 506 MB）。对照实验：
   一次普通的 512 MB `malloc` 写入**看得见**（+513 MB）。所以"内存涨没涨"不能只问
   footprint——报告里每一处都同时给"账面"和"读写之后"两栏。
3. **迟滞的收敛会被"扫描时机"骗。** 第一版量收敛只 `drain` 一次就宣布"1 轮扫描后
   停住"，报的是 1/2；真实稳定点是 1/4。原因是降级每轮只走一级，而扫描只在相机写入
   与解码完成时触发——**空闲不会自己收敛**。改法是每次轻推相机 1 个世界单位强制一次
   扫描，并要求连续两轮不变才算收敛。
4. **"清了缓存的首扫"看起来没清**——报告里每个 pass 的缓存行会打印在它自己的
   标题**之上**，我把冷扫那一行读成 0 命中，差点判定 `clearCacheFirst` 是坏的。
   实际是输出顺序错了，代码没错。**测量台自己也会有"看起来像 bug"的输出。**
5. **迟滞必须有一条"该降就降"的反向断言。** 只有"不降档"那一条的话，一个
   "永远不降档"的实现在断言上完全通过——而那是比抖动更糟的缺陷。
6. **落点压在档位边界上的断言等于没验。** 反向断言的第一版缩到 0.4 倍，需求正好是
   480（1/8 档的宽度），浮点误差让"刚好覆盖需求"在相邻两档之间跳，缺陷因此藏住了。
   改成 1/3 倍（需求 400，离两侧边界都有两成余量）才有效。**测试的落点要落在
   档位内部，不能压在边界上。**
7. **两张内容快照不可逐字节比对。** `SyntheticImageProvider.makeAssets` 用
   `Asset(id: AssetID(), …)`——**每个进程一份新 UUID**，合成图的噪声种子由它派生，
   所以每次跑出来的画面内容本来就不一样（实测：同一二进制连跑两次，2560×1600 的
   像素流不同）。B2 重拍快照时我先按"内容变了 = 渲染变了"查了一轮才发现是素材随机。
   **空画布那 6 张是逐字节稳定的**（B1 → B2 一字不差），可以做回归证据；两张内容图
   只能靠眼睛看。要让内容快照也能逐字节比对，得先让演示素材的 ID 确定化——下一轮的事。
